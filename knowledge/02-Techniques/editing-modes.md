# Режимы редактуры (editing modes)

> [!info] Зачем эта заметка
> «Отредактируй текст» — неоднозначная задача. Иногда просят вычитать опечатки, иногда — переписать заново. Ошибка режима дороже ошибки стиля: deep-перестройка юридического письма или proofread-правки текста, который просили «сделать живым», одинаково бесполезны. Эта заметка фиксирует четыре режима, разрешённые для каждого фазы и правило возврата исходника.

## 1. Четыре режима

| Режим | Что делает | Что НЕ делает | Типичный запрос |
|---|---|---|---|
| **proofread** | Исправляет опечатки, грамматику, пунктуацию, согласование | Не меняет лексику, порядок слов, структуру | «вычитай», «проверь ошибки» |
| **light** | Правит ясность: двусмысленности, тяжёлые конструкции, очевидный канцелярит | Не меняет ритм, голос, порядок абзацев | «поправь, чтобы читалось» |
| **style** | Меняет ритм и естественность: длина предложений, переходы, живость | Не перестраивает структуру аргументации | «сделай живее», «убери AI-шность» |
| **deep** | Перестраивает: порядок, объединение/разбиение абзацев, усиление аргументации | Не меняет смысл, не добавляет фактов | «перепиши», «сделай из этого статью» |

Глубина растёт сверху вниз. Каждый следующий режим включает полномочия предыдущего.

## 2. Режимы и фазы пайплайна

Скилл `humanize-editor` работает фазами: **STRIP** (удаление AI-маркеров), **TIGHTEN** (сокращение по Williams), **RELY** (iceberg-удаления, недосказанность), **REBUILD** (перестройка конструкций, RU). Режим определяет, какие фазы разрешены:

| Фаза | proofread | light | style | deep |
|---|---|---|---|---|
| STRIP | ❌ | ✅ | ✅ | ✅ |
| TIGHTEN | ❌ | частично* | ✅ | ✅ |
| RELY | ❌ | ❌ | условно** | условно** |
| REBUILD | ❌ | ❌ | ❌ | ✅ |

\* TIGHTEN в light — только удаление слов-пустышек («in order to», «the fact that»), без сокращения содержательных повторов.

\** RELY **запрещён по умолчанию при редактуре существующего текста.** Разрешён только в style/deep и только для художественного или разговорного регистра.

> [!warning] Почему RELY под особым контролем
> RELY (iceberg, недосказанность — см. [[sufficiency-and-underspecification]]) удаляет содержание, которое читатель «восстановит сам». Для собственного текста автора это законно. Для **чужого текста, который нам доверили отредактировать**, — нет: мы не знаем, что читатель автора восстановит, а что потеряет. Условие разблокировки: режим style/deep **и** регистр художественный/разговорный **и** каждое удаление проходит сверку `meaning_map` ([[meaning-preservation]]) со статусом «удалено-как-дубликат» или явным обоснованием.

## 3. Выбор режима

### 3.1. По запросу пользователя (приоритет)

Явная просьба бьёт всё остальное:

| Фраза пользователя | Режим |
|---|---|
| «проверь ошибки», «вычитай», «опечатки» | proofread |
| «поправь, чтобы читалось», «сделай понятнее» | light |
| «сделай живее», «убери канцелярит/AI-шность» | style |
| «перепиши», «сделай из этого X», «перестрой» | deep |

Если запрос неоднозначен («отредактируй») — выбирать по жанру и аудитории (ниже), при сомнении брать **более мелкий** режим и сказать об этом: «Отредактировал в режиме light; если нужна перестройка — скажите».

### 3.2. По жанру

| Жанр | Режим по умолчанию | Почему |
|---|---|---|
| Юридический текст, договор | proofread | Каждое слово имеет юридическое значение |
| Техническая документация, инструкция | proofread–light | Пропущенный шаг = сломанная инструкция |
| Медицинский/финансовый текст | proofread–light | Цена ошибки — здоровье/деньги читателя |
| Деловое письмо, служебная записка | light | Ясность важна, голос — нет |
| README, описание проекта | light–style | Технический, но читают люди |
| Пост в блог, статья | style | Голос и ритм — часть ценности |
| Эссе, колонка, художественный текст | style–deep | Текст = автор, редактируется глубоко |
| Черновик «сделай из этого статью» | deep | Пользователь явно просит перестройку |

### 3.3. По аудитории

| Аудитория | Сдвиг режима |
|---|---|
| Эксперты (свои) | Можно глубже: меньше пояснений, больше доверия |
| Новички | Мельче: объяснения и шаги — не «вода», не трогать |
| Широкая публика | Мельче: риск двусмысленности выше, чем выгода от ритма |
| Регулятор, проверяющий | Только proofread |

## 4. Тест целевого читателя

После редактуры в любом режиме глубже proofread — один вопрос:

> **Получит ли целевой читатель те же сведения и сможет ли выполнить ту же задачу без дополнительных предположений?**

- «Те же сведения» — сверка с `meaning_map`, раздел 3 в [[meaning-preservation]].
- «Ту же задачу» — если текст инструктирует (установить, настроить, решить), читатель результата должен суметь это сделать, не догадываясь о пропущенном.
- «Без дополнительных предположений» — запрет на iceberg-удаления, кроме явно разрешённых условий RELY.

Тест не проходит → правки откатываются до прохождения, а не «оставляем, звучит же лучше».

## 5. Правило возврата

> [!important] Редактура не обязана что-то менять
> Если текст уже хорош — вернуть исходник почти без изменений и сказать об этом прямо: **«текст уже хорош, вот две мелкие правки и почему больше не трогаю»**.

Это не лень, а профессиональная позиция:

1. **Редактура ради редактуры — вред.** Каждая правка несёт риск смыслового повреждения ([[meaning-preservation]], раздел 8). Если выгоды нет, остаётся только риск.
2. **Метрика «сколько изменено» ложная.** Ценность редактора — в результате, не в количестве красного в diff. Хирург не режет «чтобы было видно работу».
3. **Умение сказать «уже хорошо» — калибровка.** Редактор, который всегда находит что переписать, не различает хорошее и плохое.

Признаки текста, который стоит вернуть почти как есть: читается вслух без спотыканий; числа и условия на месте; нет AI-маркеров из STRIP-списка; ритм соответствует жанру; авторский голос узнаваем.

## 6. Примеры выбора режима

### 6.1. Запрос «вычитай договор»

Режим: **proofread**. Исправляем «в течении» → «в течение», запятые. Не трогаем «стороны договорились о нижеследующем» — это жанровая норма, а не канцелярит.

### 6.2. Запрос «сделай README живее»

Режим: **style**. STRIP + TIGHTEN полностью. RELY — только если README разговорный (например, для разработчиков, с «мы»). Шаги установки не сокращать: тест целевого читателя для инструкции — «сможет ли новичок установить».

### 6.3. Запрос «перепиши мой черновик в статью»

Режим: **deep**. Разрешён REBUILD: меняем порядок, сливаем абзацы, строим арку. Всё равно обязательна сверка `meaning_map` — перестройка структуры не лицензия на потерю оговорок.

### 6.4. Неоднозначный запрос «отредактируй пост в блог»

Режим по умолчанию для блога — style, но запрос мелкий → берём **light**, сообщаем: «Сделал light-правку. Если хотите глубже (ритм, перестройка) — скажите, это style/deep».

## 7. Связь с другими принципами

| Связь | Как работает |
|---|---|
| **[[meaning-preservation]]** | Все режимы глубже proofread обязаны пройти двустороннюю сверку. Режим задаёт глубину, но не освобождает от сохранения смысла. |
| **[[sufficiency-and-underspecification]]** | Краткость — инструмент style/deep. В proofread/light текст не сокращается, даже если «можно короче». |
| **[[voice-and-tone]]** | Голос добавляется в style/deep. В proofread/light чужой голос не трогаем — даже «безликий». |

## 8. Чеклист выбора и возврата

1. Есть явный запрос пользователя? → режим из раздела 3.1.
2. Нет → жанр (3.2) + аудитория (3.3); при сомнении — мельче, с явным уведомлением.
3. Режим выбран → фазы по таблице раздела 2. RELY — только при выполнении условий.
4. Редактура сделана → тест целевого читателя (раздел 4).
5. Diff почти пуст и правок по делу нет → вернуть исходник со словами «текст уже хорош», не выдумывать правки.
