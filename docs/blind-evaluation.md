# Слепая человеческая оценка правок

Протокол проверки того, что агент редактуры **сохраняет смысл** исходного текста и при этом
не ухудшает его. Документ описывает процедуру для 2–3 независимых читателей и то, как она
связана с машинной проверкой `scripts/check-editing-output.sh`.

---

## 1. Зачем нужна человековая часть

Машинный валидатор (`scripts/check-editing-output.sh`) проверяет инварианты, которые видны
по ключевым словам: числа, утверждения, условия, исключения, терминологию, модальность,
запрещённые добавления, «хороший текст не переписан зря». Он не умеет оценивать:

- **ясность** — стал ли текст понятнее после правки;
- **грамотность** — появились ли ошибки, которые не ловит проверка чисел и терминов;
- **естественность** — не звучит ли результат как сгенерированный;
- **соответствие жанру** — уместен ли регистр и тон (письмо, README, научная оговорка, худ текст);
- **общее впечатление** — «стало ли лучше», даже если формально всё сохранилось.

Кроме того, машинная проверка по определению опирается на список `required_preservation`
из фикстуры. Если этот список неполон, валидатор молчит, а человек заметит, что из текста
пропал целый абзац. Поэтому человеческая часть — не «подтверждение», а независимый канал,
который умеет видеть то, чего нет в списке.

Цель протокола: **измерить долю пар «исходник → правка», где правка не хуже исходника**
по каждому критерию, и зафиксировать решение «принято / не принято» по заранее
зафиксированному порогу.

---

## 2. Дизайн оценки

**Материал.** Пары вида «исходник / правка», построенные по фикстурам из
`tests/fixtures/editing/`. Для каждой фикстуры берётся:

- **исходник** — секция `## Source` (что подали агенту);
- **правка** — результат работы агента (файл, который агент сохранил как ответ).

**Слепота.** Читатель не знает, в какой колонке исходник, а в какой — правка. Он не знает,
какой это фикстуре, в каком режиме шла правка (`proofread` / `light` / `style` / `deep`),
как выглядит эталон (`## Gold edit`) и кто именно правил — человек, модель или другая
модель. Ни одно из этих сведений не показывается до сбора всех протоколов.

**Рандомизация.** В каждой паре порядок колонок выбирается случайно (coin flip), и пара
получает случайный номер (`P-07`, `P-13`, …) в общем списке. Номера идут не по порядку
фикстур, чтобы читатель не мог догадаться о типе правки по соседним парам. Если читатель
работает с двумя колонками на экране, порядок колонок должен отличаться от порядка
предыдущей пары у этого же читателя — иначе он начнёт сравнивать «левую колонку с
прошлой парой» и выравнивать оценки.

**Независимость.** Читатели работают по отдельности, не видят оценок друг друга и не
обсуждают тексты до сдачи протоколов. Каждый заполняет **свой** экземпляр таблицы из
раздела 5. После сбора протоколы сводятся по правилу из раздела 4.

**Сколько читателей.** Минимум два (тогда расхождения разбираются арбитром), оптимально
три. Если читателей меньше двух, протокол считается непроведённым: один человек не
заменяет независимую проверку.

**Время.** 3–5 минут на пару. Если пара вызывает сомнения — отметка в поле «Заметки» и
переход дальше, а не спор о трактовке.

---

## 3. Критерии и шкала

Каждая пара оценивается по пяти критериям. Шкала одинаковая для обоих текстов в паре:

| Балл | Значение |
|---|---|
| 1 | очень плохо: текст нечитаем, ошибки, или содержание искажено |
| 2 | плохо: читается с трудом, есть заметные дефекты |
| 3 | приемлемо: текст работает, но заметно слабее другого текста в паре |
| 4 | хорошо: дефектов почти нет, читается легко |
| 5 | отлично: образец для этой задачи |

### 3.1. Критерии

1. **Смысл** — совпадает ли содержание с исходником. Считаются расхождениями: потерянные
   факты, числа, условия, исключения; добавленные факты; усиленная или ослабленная
   модальность («может» → «снижает», «вероятно» → «доказуемо»); изменённый смысл термина;
   потерянная оговорка.
2. **Ясность** — понятен ли текст с первого прочтения, однозначен ли он, нет ли канцелярита,
   перегруженных конструкций, лишних вводных.
3. **Грамотность** — орфография, пунктуация, согласование, типографика (кавычки, тире,
   регистр терминов, код и команды в моноширинном виде).
4. **Естественность** — звучит ли текст как написанный человеком в этой задаче, или как
   сгенерированный (ритуальные вступления, «в современном мире», «нельзя не отметить»,
   одинаковая длина предложений, пустые абзацы).
5. **Соответствие жанру** — уместен ли тон и регистр: деловое письмо, README, научная
   оговорка, инструкция, экспертный пост, художественный текст.

### 3.2. Отдельный вопрос (обязательный)

Кроме баллов читатель отвечает на один вопрос по каждой паре:

> **«Осталось ли в правке что-то важное, чего нет в исходнике?»** — да / нет.
> Если «да» — что именно (цитата).

Вопрос ловит выдуманные факты, добавленные примеры и «улучшения», которых не просил
заказчик. Ответ «да» — это не просто низкий балл: это отдельная находка, которая
разбирается адресно (см. раздел 7).

Дополнительно (в свободном поле «Заметки»): «потерялось ли что-то важное из исходника?» —
формулировка симметрична вопросу выше и ловит пропажу, которую не видно в списке
`required_preservation`.

## 4. Правило подсчёта и порог приёмки

### 4.1. Что значит «правка не хуже»

Для каждой пары и каждого критерия:

```
не хуже  ⟺  балл(правка) ≥ балл(исходник)
```

Равенство считается «не хуже»: если правка не отличается по критерию, она не ухудшила его.

### 4.2. Доли

Для каждого критерия:

```
доля_не_хуже(критерий) = число пар, где правка не хуже / число всех оценённых пар
```

Отдельно считается:

```
доля_не_хуже(смысл)      — главная метрика
доля_пар_без_потери_смысла — то же самое, отдельным именем для отчётности
доля_пар_с_добавленным    — доля пар с ответом «да» на вопрос 3.2
```

### 4.3. Порог приёмки

| Метрика | Порог |
|---|---|
| Доля пар без потери смысла | **≥ 85 %** |
| Доля пар без потери смысла (критерий «Смысл», строгий вариант: доля пар, где правка **строго** не хуже и ни один читатель не отметил потерю) | ≥ 70 % |
| Доля пар «не хуже» по критериям «Ясность», «Грамотность», «Естественность», «Соответствие жанру» | ≥ 70 % по каждому критерию |
| Пары с добавленным важным содержанием (вопрос 3.2) | 0 |
| Грубые нарушения смысла, найденные машинной проверкой (`FAIL` в логе валидатора) | 0 |

Итоговое решение:

- **принято** — все пороги из таблицы выполнены;
- **принято с замечаниями** — смысл в порядке, но один из второстепенных критериев
  ниже 70 % (тогда в замечаниях указывается, какой и на сколько);
- **не принято** — любой порог по смыслу нарушен или есть пары с добавленным содержанием.

### 4.4. Как сводить оценки нескольких читателей

1. По каждой паре и критерию берётся **медиана** баллов читателей (при двух читателях —
   меньший из двух баллов, это консервативное правило).
2. Если по критерию «Смысл» баллы читателей расходятся на 2 и больше (например 2 и 4),
   пара отправляется третьему читателю (или арбитру из состава команды). В протокол идёт
   медиана трёх.
3. Решение «не принято» принимается, если так решило большинство читателей. Мнение
   одного расходящегося читателя фиксируется в разделе «Замечания», а не отбрасывается.
4. Все расхождения фиксируются: список пар, где один читатель поставил «хуже», а другой
   «не хуже», — это самая полезная часть отчёта, он показывает, где фикстура или инструкция
   неоднозначны.

### 4.5. Как посчитать (необязательный скрипт)

Протоколы собираются в CSV (раздел 5). Достаточно стандартной библиотеки Python:

```python
import csv, collections, statistics
rows = list(csv.DictReader(open("protocol.csv", encoding="utf-8")))
by_pair = collections.defaultdict(dict)          # pair -> reader -> {criterion: score}
for r in rows:
    by_pair[r["pair"]][r["reader"]][r["criterion"]] = int(r["score_source"]), int(r["score_edit"])
for pair, readers in by_pair.items():
    for criterion, scores in readers.items():
        src = statistics.median(s for s, _ in scores)
        edit = statistics.median(e for _, e in scores)
        verdict = "не хуже" if edit >= src else "хуже"
        print(pair, criterion, src, edit, verdict)
```

Доля «не хуже» по критерию = доля строк с `verdict == "не хуже"`.

## 5. Форма протокола

Каждый читатель заполняет **свой** экземпляр. Формат — одна строка на пару и критерий
(это удобно для CSV и для сводной таблицы):

```csv
pair,reader,criterion,score_source,score_edit,verdict,added_important,notes
P-03,R1,meaning,3,4,не хуже,нет,
P-03,R1,clarity,4,4,не хуже,нет,-
P-03,R1,grammar,3,3,не хуже,нет,-
P-03,R1,naturalness,4,2,хуже,нет,«в современных условиях…» — шаблонная вставка
P-03,R1,genre,3,4,не хуже,нет,-
P-03,R1,added,3,3,не хуже,да,в правке появилось «p99 составил 12 мс»
```

Поля:

| Поле | Значение |
|---|---|
| `pair` | анонимный номер пары (`P-01`, …) |
| `reader` | код читателя (`R1`, `R2`, `R3`) |
| `criterion` | `meaning` / `clarity` / `grammar` / `naturalness` / `genre` |
| `score_source` | балл текста в колонке A |
| `score_edit` | балл текста в колонке B |
| `verdict` | `не хуже` / `хуже` (заполняется по правилу ≥, можно не заполнять — считается автоматически) |
| `added_important` | ответ на вопрос 3.2: `да` / `нет` (одна строка на пару, в остальных строках пары — пусто) |
| `notes` | что именно насторожило, цитата, падение по какому критерию |

Сводная таблица (после сбора всех протоколов) — по парам:

| Пара | Машина | Смысл | Ясность | Грамотность | Естественность | Жанр | Добавлено важное | Вердикт |
|---|---|---|---|---|---|---|---|---|
| P-03 | PASS | 4/3 | 4/4 | 3/3 | 2/4 | 4/3 | нет | не хуже |
| P-07 | FAIL: numbers | 2/5 | … | … | … | … | нет | хуже |

Формат `4/3` — «оценка исходника / оценка правки».

Для бумажного варианта — та же таблица, распечатанная как сетка: строки — пары, колонки —
критерии, в каждой ячейке два числа (исходник и правка).

## 6. Инструкция для читателей

Вы получите список пар. В каждой паре два текста: A и B. **Какой из них исходный, а какой
отредактированный — знать не нужно и не нужно выяснять.**

1. Прочитайте оба текста в паре. Оценивайте **каждый текст сам по себе**, а не сравнивайте
   их «на глаз» и не ищите в правке отличия от первого текста.
2. Поставьте баллы по пяти критериям (шкала 1–5 из раздела 3) отдельно для A и B.
3. Ответьте на вопрос: осталось ли в тексте B что-то важное, чего нет в A? Если да —
   процитируйте.
4. Запишите в «Заметки» всё, что показалось подозрительным: выдуманные числа, пропущенные
   оговорки, «нейросетевые» обороты, несоответствие регистра.
5. Не правьте текст. Вы оцениваете, а не редактируете.
6. Не обсуждайте пары с другими читателями до сдачи протокола: иначе оценки перестают быть
   независимыми.
7. Если сомневаетесь между двумя баллами — ставьте меньший и пишите сомнение в заметки.
   Лучше «3 и сомнение», чем выдуманная точность.
8. Уложитесь в 3–5 минут на пару. Если времени не хватает — отметьте это в протоколе:
   неполный протокол честнее отсутствующего.

Читателю не показывают: фикстуру, эталонную правку (`## Gold edit`), список
`required_preservation`, режим правки, промпты агента и инструменты, которыми он правил.

## 7. Чек-лист безопасности и слепоты

**Обезличивание (до сборки пар).**

- Убрать имена людей, названия компаний и продуктов, идентификаторы, номера заявок,
  внутренние ссылки и URL, адреса, телефоны, даты, привязанные к конкретным людям.
- Заменить их нейтральными плейсхолдерами одинаковой длины, чтобы не менять объём текста.
- Не публиковать исходные данные в открытых сервисах: если для подготовки пар
  используется внешний LLM-ассистент, это делается на обезличенных текстах.

**Слепота (до конца оценки).**

- Читатель не знает, кто и чем правил, в каком режиме шла правка и что считается эталоном.
- Порядок колонок в паре и порядок пар — случайные; генерация случайна и воспроизводима
  (зафиксировать seed в протоколе).
- Названия фикстур и их категории не показываются: `already-good-3` выдаёт жанр и сразу
  подсказывает, что текст трогать не следовало.
- Эталонная правка (`## Gold edit`) не показывается до сбора всех протоколов: сравнение с
  эталоном заранее настраивает читателя на «искать отличия».
- ИИ-происхождение правок не раскрывается до конца оценки. После сбора — раскрывается
  обязательно: иначе невозможно честно сказать, чья это была правка.

**Приватность и этика.**

- Исходные тексты и протоколы хранятся локально; наружу отправляются только обезличенные
  пары и обезличенные протоколы.
- Участники могут отказаться от оценки или попросить удалить свои данные до сведения.
- Оценка не используется для оценки людей: оценивается пассивность правки, а не автор.

**Разбор находок (после сбора).**

- Читатель нашёл потерю смысла там, где машинная проверка сказала `PASS` → это дефект
  фикстуры: `required_preservation` неполон. Фикстуру дополняют, а не «чинят» оценку.
- Машинная проверка нашла `FAIL`, а читатели не заметили → дефект проверки или слишком
  «свой» способ выражения в фикстуре. Проверку правят.
- Читатели нашли выдуманный факт → это самое важное; фикстуру и/или промпт агента правят
  в первую очередь, результат переделывается.

## 8. Связь с машинной частью

### 8.1. Что где лежит

| Артефакт | Путь | Кто делает |
|---|---|---|
| Фикстуры (исходник, эталон, `required_preservation`, `forbidden_additions`) | `tests/fixtures/editing/*.md` | команда, вручную |
| Правка агента | `out/<fixture-id>.output.md` | агент редактуры |
| Машинный лог проверки | `out/<fixture-id>.machine.txt` | `scripts/check-editing-output.sh` |
| Протокол читателя | `out/protocol-<reader>.csv` | читатель |
| Сводный отчёт | `docs/blind-eval/<дата>-report.md` | команда |

Каталог `out/` — рабочий: он создаётся под конкретный прогон и в репозиторий не попадает.
Фикстуры, валидатор и этот документ — единственное, что хранится постоянно.

### 8.2. Как связаны

```
tests/fixtures/editing/*.md
        │  (Source → агент → out/<id>.output.md)
        ▼
scripts/check-editing-output.sh <out> <fixture>   →   out/<id>.machine.txt
        │  PASS/FAIL по инвариантам смысла
        ▼
слепые пары (Source / output) → протоколы R1..R3 → сводный отчёт
```

**Разделение труда:**

| Что ловит машина | Что ловит человек |
|---|---|
| потерянное число, выдуманное число | изменённый смысл без изменения чисел |
| потерянное утверждение, условие, исключение | потерянный кусок текста, не входящий в `required_preservation` |
| потерянная терминология | термин, оставшийся, но в другом смысле |
| ослабленная/усиленная модальность | модальность, формально сохранённая, но перенесённая на другое утверждение |
| запрещённое добавление | добавление, не описанное в `forbidden_additions` |
| «хороший текст переписан зря» | общее качество, ритм, тон, «человечность» |

**Как именно проверяется модальность.** Валидатор ищет в `required_preservation.uncertainty`
маркер модальности («может», «вероятно», «нет», «не исключено» и т. п.) и требует, чтобы рядом
с соответствующим утверждением в тексте остался маркер той же семьи
(эпистемическая: возможность/вероятность; ограничение; обязанность). «Может» может законно
превратиться в «по-видимому» — это одна семья. А вот «скорее всего» → «точно» или
«не знала» → «знала» считаются нарушением: рядом с утверждением появляется категоричное
слово («точно», «доказано», «гарантированно»).

**Как проверяется сохранность утверждения.** Ключевые слова каждого пункта
`required_preservation` сопоставляются с текстом по основам слов (стемминг + нечёткое
сравнение), поэтому переформулировка не считается потерей. Порог для каждого пункта —
эталонная редакция из той же фикстуры: результат должен сохранять не меньше ключевых слов,
чем эталон (с допуском 0.2 и нижней границей 0.1). Если эталон сохраняет утверждение
полностью, порог высокий; если эталон переформулировал его сильно — порог снижается.
Отрицания («не», «нет», «без») проверяются отдельно и жёстко: исчезновение отрицания —
это всегда нарушение, даже если остальные слова на месте.

**Порядок работы:**

1. Прогнать агента по всем фикстурам, сохранить результаты в `out/`.
2. Прогнать машинную проверку по каждому результату. Каждый `FAIL` — приоритетный разбор.
3. Отдельно отметить пары, прошедшие машинную проверку, но подозрительные для человека.
4. Собрать слепые пары (рандомизация), раздать читателям.
5. Свести протоколы, посчитать доли по разделу 4, принять решение по порогам.
6. Разобрать находки: фикстуры, проверка, промпты агента.

### 8.3. Команды

```sh
# машинная проверка одной пары (исходник → правка агента)
bash scripts/check-editing-output.sh out/expert-post-1.output.md \
     tests/fixtures/editing/expert-post-1.md

# машинная проверка всех результатов разом
for f in tests/fixtures/editing/*.md; do
  id="$(basename "$f" .md)"
  bash scripts/check-editing-output.sh "out/$id.output.md" "$f" > "out/$id.machine.txt" || true
done

# проверка целостности самих фикстур и эталонов
bash scripts/test-editing-fixtures.sh
bash scripts/check-editing-output.sh --selftest
```

`--selftest` создаёт во временном каталоге корректную и некорректную правку и убеждается,
что валидатор принимает первую (exit 0) и отклоняет вторую (exit 1), а также прогоняет
эталонные правки всех фикстур. Это дешёвый способ узнать, что валидатор не сломался,
прежде чем собирать живые оценки.

## 9. Что этот протокол не доказывает

- **Он не доказывает, что агент «хорош» в абсолюте.** Он доказывает, что на конкретном
  наборе фикстур агент не хуже исходника по заданным критериям.
- **Он не заменяет машинную проверку.** Оценка читателя субъективна, а смысловые
  инварианты проверяются детерминированно — поэтому сначала машина, потом человек.
- **Он не ловит выдуманные факты автоматически.** Вопрос 3.2 снижает риск, но не
  устраняет его; строгий фильтр выдуманных чисел — машинная проверка.
- **Один набор фикстур — это выборка.** Значимость порогов (85 % / 70 %) осмысленна внутри
  одного корпуса; при смене корпуса пороги пересматриваются, а не переносятся молча.
